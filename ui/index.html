Grit Remover

An unapplied cash resolver agent

A customer's virtual account number already matches a payment that arrives for the exact amount. This agent handles the rest: wire fees, partials, overpayments, batch payments, two invoices at the same amount, and payments sent to the main account number. It applies the ones it can prove and hands you a short, explained queue for everything else. Every number below comes from a recorded eval run you can scrub through.

Auto-apply bar

How sure the agent must be before money moves onto an invoice without a person looking. This is a product decision. Lower it and more payments reconcile themselves; the code guardrails still have to agree either way.

0.90

How a payment flows

  1. Code

    Gather evidence

    Note which account number the money arrived on, recover invoice numbers from messy memos, match the payer against names this customer has paid from before, find exact amounts and invoice combinations that sum to the deposit.

  2. Model

    Propose

    Decide what the payment is: which invoices, any fee or partial, a calibrated confidence, and one sentence a business owner can read.

  3. Code

    Decide

    Auto-apply only if amounts reconcile to the cent, one customer, two independent signals (payer and reference or amount), nothing else fits as well, and no partials or overpayments.

  4. Product

    Act

    Apply and log it, or put it in the queue with the suggested match and the reason it stopped.

What it costs to run

Model cost is measured, not guessed: token counts from all 297 agent calls across the three test sets, priced at list rates, with the instructions every call shares cached. Time saved uses the eval's time assumptions and compares the agent with built-in matching alone, at the 0.90 bar.

Synthetic data: 30 fictional businesses across tech, professional services and real estate, with payments written to stress the cases that break rules (mangled memos, wire fees, batch payments, parent-company payers, look-alike amounts, refunds and transfers). About 55% of invoice payments arrive on the customer's virtual account number; that share is an assumption, and real traffic sets it. Built-in matching follows the publicly documented behavior: exact amount on the virtual account, with short payments and overpayments left unreconciled. Real bank feeds are messier; the next step is shadow mode on real traffic.
